K2 Dough Scoring

An ABB IRB 1200 with an ultrasonic knife scores every dough piece on trays that pass back to back on a moving belt. Cut lines come from each piece's 3D shape; a PPO policy steers the knife tip; a scheduler fed by encoder ticks decides what to cut next. Everything here runs in Isaac Sim / Isaac Lab on the GPU box.

Architecture

Three stages: build the scene and the training data once, train the policy, then run the line. The line runtime only talks to the outside world through two interfaces — encoder ticks and tray messages — so the same code can later be fed by the real PLC and AI_CORE[8][9].

What was built, step by step

  1. Found and measured the knife. The tool is tn__00RB025COG2_pGu4 inside the A-900023 CAD assembly (93 meshes, ~40 × 31 × 31 cm, scaled ×39 from inches). Rendered it isolated; the first automatic mount guess landed on the splash-guard rim, fixed by using the ATI 9120 tool-changer plate (Solid5, 60 mm) as the flange face. TCP = blade tip; blade 2.5 mm × 25.5 mm, 32° off the flange axis[1].

  2. Robot kinematics. Forward kinematics from USD/ABB-IRB1200.urdf with the side-mounted base (0.225, 0, 1.961 m, +90° about Y); checked against the scene: tool0 at (1.114, 0, 1.428) m at zero joints. Numeric damped-least-squares IK on the TCP pose.

  3. Reach study. The camera-station tray (x = −1.43 m) is out of reach. Solved IK for a 7 × 7 grid over the tray, blade vertical, cutting along and across the belt: the whole tray is reachable for tray positions x = 0.4–0.9 m → station at 0.65 m[2].

  4. Scene 006. K2-CV-STEP-006-CUT.usd from 005 (004/005 untouched, checked by checksum). Copying the knife failed because it is defined in the referenced CAD file, fixed by referencing it from that file onto tool0; the floating knife is deactivated; TCP marker prim added; tray moved to the station (belt top 0.914 m, tray bottom 0.915 m)[3].

  5. Cut lines. From each piece's mesh: long pieces (aspect > 1.4) along their length, round ones along the belt; middle 80%; 3 mm under the top surface (exact, from the mesh triangles) every 5 mm; approach/retract 3 cm above[4]. You asked to use the procedural dough generator rather than RealSense crops, so pieces come from DoughSDG.

  6. Training library. 900 random trays (1–5 pieces, long and round, any rotation) across the reach window → 2,610 cuts with IK start poses (36 unreachable or too long dropped)[5].

  7. Encoder and adaptive scheduling (your requirements). Trays arrive back to back with any number of pieces; belt position only from 32-bit encoder ticks; one JSON message per tray at the photoeye; earliest-deadline-first scheduling with misses reported[8][9].

  8. RL environment. Isaac Lab DirectRLEnv, robot only (the 80 MB factory is not cloned). The reference point travels the cut line at 50 mm/s while the line drifts with the belt; PPO outputs knife-tip moves that differential IK turns into joint targets[6].

  9. Feasibility check. A scripted follower through the same IK kept 93% of cut steps in tolerance (errors at the plunge corner) — the task is achievable; PPO has room to anticipate the corner.

  10. Training v1. 1,024 envs, 1,500 iterations, ~36 min: 98.1% of cut steps in tolerance, 97.5% of cuts ≥90% in tolerance. Episode “success” stayed at 0: the policy learned not to finish because finishing ended its reward (reward hacking) — handled in the runner[7].

  11. Line runner bugs found and fixed. Idle loop never advanced the simulation once the robot was home (fixed: always step); Isaac Sim hung in close() after the report was written (fixed: exit directly); stale runner processes from timeouts (killed); the first scheduler window (0.40–0.95 m) missed 4/16 pieces (fixed: training-coverage window 0.05–1.10 m + IK check)[10].

  12. Viewing and tuning. Live window with planned (yellow) and actual (red) cut lines and --hold; reward weights and settings exposed as --env KEY=VALUE, saved as env_cfg.json next to the policy and loaded by the runner.

How to tune

Every setting below is a CutEnvCfg field and can be set at launch with --env KEY=VALUE; the values used are saved with the policy and reused by the runner, so training and evaluation always match[6a].

Settingv1Raise it when…Lower it when…
belt_speed_max0.03the line runs faster, or the 30 mm/s results are weak (train past the line speed, e.g. 0.04)—
cut_speed0.05you need throughput (more pieces per tray at high belt speed)depth errors grow
counts_per_m10000set to the real encoder; retrain if far from 10,000
tol_depth / tol_lateral / tol_tilt_deg0.001 / 0.002 / 5change the quality spec (also the runner's pass mark)
w_track_fine, track_fine_m1.0, 0.002cuts are close but not inside ±1 mmlearning stalls early (start wider)
w_in_tol1.0the tolerance pass rate lags the mean errorit chases the bonus with jerky motion
w_rot, rot_rad0.5, 0.05blade tilt or sideways drift on cuts across the belt—
w_smooth, w_action0.05, 0.01motion is jitteryit lags the reference
w_success5“episode_success” stays 0 (v1 reward hacking): try 20+—
w_lost, lost_dist5, 0.04it gives up on hard cuts—
max_step_pos, max_step_rot0.004, 0.03it can't keep up at high belt speedit overshoots
start_noise0.01for robustness to imperfect transit—

PPO knobs live in train_cut_ppo.py[7]: more --num_envs (2,048 fits on the 3090) for smoother gradients; init_noise_std 0.6 → 0.4 if training is noisy at the end; entropy_coef down if the policy keeps jittering; learning_rate stays adaptive.

Tuning loop. Change one thing → check_env.py if you changed the environment → train 500 iterations → runner sweep at 0.01/0.02/0.03 m/s with the same seed → compare report.json. Keep the seed fixed so runs are comparable, then confirm on new seeds.

Line runtime

Per control step (30 Hz) tray_runner.py does what the line controller will do[10]:

  1. Read the encoder; update belt position and speed (BeltTracker).
  2. When a tray's front edge reaches the photoeye, latch the encoder count and send its tray message (pieces' cut lines in tray coordinates).
  3. If idle: ask the scheduler for the next cut — among cuts that can still be finished inside x = 0.05–1.10 m, the one whose tray leaves first, accepted only if IK reaches its start now and its end after belt drift. Cuts that can no longer be finished are marked missed.
  4. Transit to the moving approach point (≤0.35 m/s, ≤3° per step), then hand over to the policy with the same observations as training; the cut ends when the reference reaches the retract point and the tip is within 1.5 cm.
  5. Score against the true geometry: per-cut % of steps in tolerance, max depth/sideways error, max tilt; pass at ≥90%.

[8] ~/TH/Project-Manhattan/encoder.py:18 — tick_delta, SimBeltEncoder (25), BeltTracker (44)

Signed tick difference across the 32-bit wrap; the real encoder replaces SimBeltEncoder.read().

def tick_delta(new, old, bits=32):
    """Signed tick difference that survives counter wrap-around."""
    span = 1 << bits
    d = (new - old) % span
    return d - span if d >= span // 2 else d
